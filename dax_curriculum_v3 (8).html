ALL, ALLEXCEPT & ALLSELECTED
These functions modify or inspect the filter context from inside CALCULATE. They are the primary tools for building percentages, ratios, and comparisons across the matrix.
Prerequisites: Chapter 1 (Filter Context) and Chapter 4 (CALCULATE).
The Three Functions
ALL(Table or Column)
Removes all filters from the specified table or column. Used as a CALCULATE modifier to ignore the visual's filter context and see the full dataset.
[% of Total] = DIVIDE( [Total Sales], CALCULATE([Total Sales], ALL(DimProduct)) )
ALLEXCEPT(Table, Col1, Col2…)
Removes all filters except the ones you list. Useful for % within a group — keep the group filter, remove everything else.
[% of Category] = DIVIDE( [Total Sales], CALCULATE([Total Sales], ALLEXCEPT(DimProduct, DimProduct[CategoryName])) )
ALLSELECTED(Table or Column)
Removes internal filters (from the visual) but keeps external filters (from slicers, page filters, other visuals). Used when the denominator should respect what the user selected.
[% of Selection] = DIVIDE( [Total Sales], CALCULATE([Total Sales], ALLSELECTED(DimProduct)) )
ALL: Modifier vs Table Function
ALL as a CALCULATE modifier
When ALL appears directly inside CALCULATE, it removes filters. The filter context is modified before the expression evaluates.
CALCULATE([Total Sales], ALL(DimProduct[BrandName])) -- Removes the BrandName filter. Expression sees all brands.
ALL as a table function
When ALL is used as an argument to another function (FILTER, SUMX, etc.), it ignores filters and returns all rows of the table regardless of context.
COUNTROWS(ALL(DimProduct)) -- Returns total product count, ignoring any filter.
ALL vs ALLSELECTED — The Key Difference

ALL — ignores everything

ALLSELECTED — respects the slicer
The denominator includes only the 2 slicer-selected channels. [% of Selection] sums to 100% within what the user chose.

Chapter 7
CALCULATE — Advanced
Multiple modifiers, REMOVEFILTERS, table-valued filters, nested CALCULATE, and how context transition works when you call a measure inside a calculated column.
Prerequisites: Chapter 4 (CALCULATE basics), Chapter 3 (Context Transition), Chapter 6 (ALL/ALLEXCEPT).
How CALCULATE processes multiple modifiers
Multiple modifiers combine with AND logic
When you pass multiple modifiers to CALCULATE, they all fire before the expression. Each modifier either adds, replaces, or removes filters. The result is the intersection of all surviving filters.
CALCULATE( [Total Sales], DimChannel[ChannelName] = "Online", -- adds channel filter DimDate[CalendarYear] = 2007, -- adds year filter ALL(DimProduct) -- removes product filter ) -- Result: Online + 2007 + all products
The order of modifiers does not matter. ALL fires before predicates only in the sense that removes happen before additions; practically, the final state is the intersection of what remains after all modifiers apply.
REMOVEFILTERS — the explicit alias for ALL
ALL as modifier — intent unclear
CALCULATE([Total Sales], ALL(DimProduct))

Does ALL mean "return the DimProduct table" or "remove filters from DimProduct"? It depends on context. Hard to read at a glance.
REMOVEFILTERS — intent explicit
CALCULATE([Total Sales], REMOVEFILTERS(DimProduct))

REMOVEFILTERS can only be used as a CALCULATE modifier. It always removes filters. The intent is unmistakable. Use it when you want to be explicit.
Table-valued filters vs predicate filters
Three ways to write the same filter
StyleExampleSpeedWhen to use
Predicate (column = value)DimChannel[ChannelName] = "Online"FastestSimple equality or IN list
FILTER(Table, condition)FILTER(DimChannel, [ChannelName] = "Online")SlowRow-level conditions, cross-column expressions
FILTER(ALL(Table), condition)FILTER(ALL(DimChannel), [ChannelName] = "Online")Slow + clears existing filter firstWhen you need to override and re-apply
FILTER(ALL(Table), col = value) is almost always wrong. It first removes all filters on the table, then applies a new one. This ignores any other active filters on that table. Use a predicate unless you specifically want to override.
Nested CALCULATE — inner wins on the same column
What happens when two CALCULATE calls filter the same column?
[Contoso Online 2007] = CALCULATE( CALCULATE( [Total Sales], DimChannel[ChannelName] = "Online" -- inner ), DimChannel[ChannelName] = "Store" -- outer ) -- Result: Online sales. Inner CALCULATE wins.

The inner CALCULATE sets ChannelName = "Online". When the outer CALCULATE tries to set ChannelName = "Store", it is too late — the inner filter already replaced it. The inner CALCULATE always wins on the same column.

Exception: KEEPFILTERS. If the inner uses KEEPFILTERS, the two filters intersect instead of the inner replacing the outer.
Context transition in a calculated column — the trap
Calling a measure in a calculated column triggers unexpected CT
-- In DimProduct (calculated column): Product Sales = [Total Sales] -- This triggers context transition! -- The current DimProduct row becomes a filter on FactSales. -- Each product row gets its own sales total — which looks correct, -- but it's a coincidence: CT added ProductKey = N as a filter.

This works when the row context uniquely identifies rows in the fact table. It breaks when:
  • The dimension has no direct relationship to the fact table
  • The calculated column is on the fact table itself (CT would filter to that single row)
  • You expect the measure to see the full dataset, not just the current row's facts
Rule: be deliberate about CT in calculated columns. If you want the measure to respect only the current row, use it directly. If you want the full dataset, wrap in CALCULATE(measure, ALL(Table)) to prevent CT.
